| # | Finding | Fix | Test |

| A | Public `seed_synthetic` action; demo accounts / quick-switch reachable in production | `/api/admin` `seed_synthetic` requires an authenticated `admin` and is refused (403) when `NODE_ENV=production`; `runSyntheticSeed()` and `createNonProductionInternalUser()` throw in production; `loginUser()` rejects `@synthetic.solob.local` accounts in production; quick-switch bar is shown only when the **server** reports `allowSyntheticQuickSwitch` (false in production) — no UI flag alone can enable it | SEC-1, SEC-2 |

Privileged/verified roles are created via `provisionVerifiedUser()` (admin → any; operator → teacher/reviewer) or the one-time `npm run db:bootstrap-admin` | SEC-3 |
| C | Raw session tokens in JSON + `localStorage` | Tokens only in `solob_session` cookie: `HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` in production, explicit expiry. No token in any JSON body; no `localStorage`/`sessionStorage` anywhere in `src/`. Same-origin client (`src/lib/core/client-http.ts`) uses `credentials: 'same-origin'` + `X-Solob-CSRF` header (double-submit, `solob_csrf` cookie) and Origin / `Sec-Fetch-Site` checks. Logout revokes server-side and clears cookies | 1, 15, SEC-4 |
| D | Hardcoded HMAC fallback in production | `validateSessionSecretConfig()` fails fast in production when `SESSION_SECRET` is missing, a known placeholder/dev value, < 32 bytes, or low entropy; called on DB readiness (startup path). Dev fallback only outside production | SEC-5 |
| E | Rate limiting keyed on fixed `127.0.0.1` / spoofable `X-Forwarded-For` | Forwarding headers are ignored unless `TRUST_PROXY=true` (see staging hardening G below: now gated by the `x-solob-proxy-secret` header); with a trusted proxy the client IP is taken `TRUSTED_PROXY_HOPS` from the right. Buckets stored in PostgreSQL (`rate_limit_buckets`, migration 002), shared across instances. Register: 15/min/client + 5/min/email; login: 15/min/client + 10/min/email | SEC-6 |
| F | Error leakage; uploads were text-only | `handleApiError()` returns generic `INTERNAL_SERVER_ERROR` for non-`AppError`s. **Additional bug found & fixed in this pass:** two separate `AppError` classes existed (`http.ts` and `rbac.ts`), so RBAC 401/403/400 errors were returned as 500 by the HTTP layer; `http.ts` now re-exports the single `rbac.ts` class. School upload accepts real `multipart/form-data` file selection; magic-byte checks (PDF `%PDF-`, ELF/PE/script rejection), MIME allowlist, size limit, owner/task authorization, private storage, and compensating delete of the stored object if the DB insert fails | 5, SEC-7, SEC-8 |

## Staging final hardening (2026-10-30)

| # | Finding | Fix | Test |
|---|---------|-----|------|
| G | Proxy header name inconsistent between code and docs, secret optional in production, `===` comparison, no startup validation | Canonical header **`x-solob-proxy-secret`** (`PROXY_SECRET_HEADER` in `src/lib/core/config.ts`); legacy name no longer accepted. `validateProxyConfig()` fails fast in production when `TRUST_PROXY=true` and `TRUSTED_PROXY_SECRET` is empty / < 32 chars / placeholder / low variety, when `TRUST_PROXY` is not `true`/`false`, or when `TRUSTED_PROXY_HOPS` is not an integer 1–10. Runs at Next.js startup (`src/instrumentation.ts`) and on every DB readiness check. Constant-time comparison (SHA-256 digests + `timingSafeEqual`). On missing/wrong secret all forwarding headers (`X-Forwarded-For`, `X-Real-IP`) are ignored; `cf-connecting-ip` is no longer trusted. Client IP = `TRUSTED_PROXY_HOPS`-th entry from the right; fewer entries than hops → untrusted | PRX-1…PRX-4 |
| H | Rate limiter did SELECT then UPDATE (race: concurrent requests could exceed max); silent per-instance memory fallback on DB error | Single atomic `INSERT … ON CONFLICT (bucket_key) DO UPDATE … RETURNING` using the DB clock (`clock_timestamp()`); window reset inside the same statement; counter capped at max+1. DB unavailable → production fails closed with `503 RATE_LIMIT_UNAVAILABLE` (no detail leak); memory fallback only outside production (disable with `RATE_LIMIT_ALLOW_MEMORY_FALLBACK=false`; `true` in production aborts startup). No schema change needed | RL-1…RL-5, EXT-2 |
| I | `.env.example` used `INITIAL_ADMIN_*` while script/docs used `BOOTSTRAP_ADMIN_*`; bootstrap was check-then-insert (concurrent runs could create several admins); bootstrap audit metadata contained the (redacted) password | Names unified to `BOOTSTRAP_ADMIN_EMAIL/PASSWORD/NAME/COUNTRY`. Bootstrap runs in one transaction with `pg_advisory_xact_lock` and claims the `system_bootstrap` singleton row (migration `003_bootstrap_singleton.sql`, PRIMARY KEY + `CHECK (bootstrap_key = 'initial_admin')`); losers roll back with `409 ADMIN_ALREADY_BOOTSTRAPPED`. Audit metadata no longer includes password; script never prints it | BOOT-1…BOOT-4, EXT-3 |

All earlier protections (A–F) are unchanged and their tests still pass.

## Remaining risks / limitations
- Without `TRUST_PROXY`, per-client throttling falls back to a fingerprint (host + UA + Accept-Language), which an attacker can vary; **production must run behind a trusted reverse proxy/gateway** (or apply gateway-level rate limiting) — see DEPLOYMENT.md.
- External PostgreSQL: the full suite was run against a real local PostgreSQL 16.14 server via `DATABASE_URL` (`pg.Pool`), but not yet against the managed staging provider (TLS, connection pooler such as PgBouncer in transaction mode — advisory xact locks are compatible, session-level features are not used).
- Proxy trust was integration-tested with a real Node `http` reverse proxy over real sockets, not with the production nginx/Caddy config; that config must be verified on staging.
- Fail-closed rate limiting means a PostgreSQL outage blocks logins/registrations (availability trade-off, by design).
- Dev-only synthetic password constant is still compiled into the client bundle for the local quick-switch; it is useless in production (synthetic logins blocked server-side), but should not be reused anywhere.
- No ESLint config: `npm run lint` is TypeScript `tsc --noEmit` only.
- No third-party penetration test, malware/AV scanning of uploads, or MFA for privileged accounts yet.
- Real payments remain disabled (`PAYMENT_PROVIDER=disabled`, live transfer → 400).
